## 三、FDE 功能清单（fde-agents :8001）

### 3.1 架构：Supervisor 多 Agent 编排（LangGraph）

主图 Supervisor 先做**意图识别**，再分发到 4 个专业子 Agent（每个都是独立子图）：

| 子 Agent | 子图 | 职责 | 输出 |
| --- | --- | --- | --- |
| 风险分析 | risk_analysis | 规则评分 + LLM 解读（金额/供应商/预算/品类等维度加权） | risk_score、risk_level、维度得分、风险点 |
| 供应商尽调 | supplier_diligence | 公开信息搜索供应商舆情，提取风险信号，LLM 生成尽调报告 | supplier_report（风险信号列表+报告） |
| 审批建议 | approval_advice | 综合风险分+尽调结果，给出 approve/reject/supplement/human 建议 | approval_decision、理由、是否需人工 |
| 异常检测 | anomaly_detection | 分析历史采购记录，识别拆分订单等异常 | anomaly_alerts 告警列表 |

> **说明**：你看到前端只有「风控分析 + 使用说明」两个页面，但这不是 FDE 的全部能力——
> 后端实际是 4 个 Agent 子图 + 1 个 Supervisor 编排图，前端「风控分析」页提交后即触发**完整 Supervisor 工作流**（4 个子 Agent 全部参与）。
> 另外 3 个 Agent 还有独立调试 API 可单独调用（见 3.2），前端页可以后续按需扩展。

### 3.2 对外 API

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/analyze` | POST | 完整风控工作流（Supervisor → 4 子图 → 结构化结果），ERP 提交采购单时调用它 |
| `/due-diligence` | POST | 单独执行供应商尽调（调试入口） |
| `/anomaly-check` | POST | 单独执行异常检测（调试入口） |

示例调用：

```
POST http://localhost:8001/analyze
{
  "request_id": 4,
  "purchase_request": { "title": "...", "total_amount": 90000, "supplier_id": 1, ... }
}

POST http://localhost:8001/due-diligence
{ "supplier_id": 1, "supplier_name": "华为技术有限公司" }

POST http://localhost:8001/anomaly-check
{ "history": [ { "supplier_id": 1, "amount": 30000, "created_at": "2026-09-20" } ] }
```

## 四、两项目联动机制

```
用户  → ERP前端(5173) 录入采购申请
        └─ POST /api/v1/purchase-requests  (draft)
        └─ 提交 POST /purchase-requests/{id}/submit  → status=analyzing
              └─ ERP 调用 FDE POST /analyze（HTTP，agent_service:8001）
                    └─ FDE Supervisor 意图识别 → 分发 4 个子图
                         ├─ risk_analysis        （风险评分）
                         ├─ supplier_diligence   （供应商尽调）
                         ├─ approval_advice      （审批建议）
                         └─ anomaly_detection    （异常检测）
                    └─ 返回 final_result {risk_score, risk_level, supplier_report, advice, alerts}
              └─ ERP 落库 apply_agent_result：
                   risk_score < 40  → 自动通过（approved）
                   risk_score ≥ 40  → 人工审批（pending_approval）
                        └─ 创建 ERP 审批记录 + 调用飞书创建审批实例
                              └─ 审批人在飞书审批中心处理
                              └─ 回调（见第五节）→ ERP 同步审批结果
```

关键点：
- **ERP 是主流程**（采购单/审批/库存），FDE 是**风控大脑**（分析/尽调/建议/告警），二者通过 HTTP 松耦合联动。
- ERP `.env` 中 `AGENT_SERVICE_URL=http://localhost:8001` 指向 FDE；FDE `erp_client.py` 可回查 ERP 采购单详情。
- 无 LLM Key 时 FDE 自动降级为规则路由（`_rule_based_supervisor`），仍可返回结构化结果。

## 五、飞书审批回调配置步骤（审批结果自动同步回 ERP）

### 5.1 现状

- ERP 已实现回调入口：`POST /api/v1/webhooks/feishu-approval`
  接收 `{ "code": "<审批实例code>", "status": "APPROVED|REJECTED|CANCELED", "comment": "..." }`
- 收到 APPROVED → ERP 审批记录与采购单变 approved；REJECTED → rejected。
- 当前端点未实现飞书签名验证（代码 TODO 标记）。

### 5.2 配置步骤（飞书开放平台 → 应用 → 事件订阅）

> ⚠️ 前提：飞书回调要求 **公网 HTTPS 可达地址**。本地 localhost:8000 无法被飞书服务器访问。
> 本地联调可用内网穿透（ngrok / frp / cpolar 等）把 8000 暴露成公网地址，或部署到公网服务器。

1. 打开[飞书开放平台](https://open.feishu.cn/app)，进入你的应用（cli_aa34921c82f8dbd8）。
2. 左侧「事件与回调」→「订阅方式」选 **将事件发送至开发者服务器**。
3. 「请求地址」填写：
   `https://<你的公网域名>/api/v1/webhooks/feishu-approval`
   （本地穿透示例：`https://xxx.ngrok-free.app/api/v1/webhooks/feishu-approval`）
4. 添加事件：搜索并订阅 **审批 → 审批实例状态变更（approval.instance.status.change）**。
5. 「加密策略」建议开启「加密」：保存后获得 **Encrypt Key** 与 **Verification Token**；
   如不加密可跳过，但生产环境强烈建议开启。
6. 保存后飞书会向该 URL 发送 **URL 校验请求（Challenge）**，需要端点返回 `{"challenge": "..."}` 才能验证通过。
7. 审批人处理审批后，飞书推送状态变更事件 → ERP 解析 instance_code + status → 同步更新审批与采购单。

### 5.3 需要补充的适配（建议下一步完成）

当前端点接收的是**简化 JSON**，飞书原生事件推送是**加密包结构**（encrypt 字段 + Challenge 校验 + 签名头）。
要让 5.2 的配置真正可用，需要把 `/api/v1/webhooks/feishu-approval` 升级为：
- 支持 URL 校验（返回 challenge）
- 校验 `X-Lark-Signature` / 解密 encrypt payload
- 解析 `event.instance_code` 与 `event.status`，再复用现有 `handle_feishu_callback`

完成此适配需要你提供（或选择不加密后仅提供 Verification Token）：
- **Encrypt Key**（若开启加密）
- **Verification Token**
- 公网回调地址（穿透后的 HTTPS URL）
