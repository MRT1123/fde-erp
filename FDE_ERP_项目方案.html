一、项目概述

1.1 什么是 FDE？

Forward Deployed Engineer（前线部署工程师）是 AI 公司派驻到客户现场、将 AI 技术嵌入真实业务流程的岗位。最早由 Palantir 推广，目前 OpenAI、Anthropic、月之暗面（Kimi）等头部 AI 公司均采用此模式。

FDE 的核心工作不是「做功能」，而是让复杂技术在真实客户业务中产生可衡量的价值。典型工作包括：

  • 深入客户现场，理解真实业务流程与痛点
  • 拆解业务流程，定义数据流与 AI 嵌入点
  • 对接客户遗留系统（ERP、OA、CRM 等）
  • 用 Agent/LLM 编排解决具体业务问题
  • 快速迭代 MVP，持续与客户共创

1.2 什么是 ERP？

本项目中的 ERP 是一个轻量级采购管理系统，聚焦采购流程的核心环节：采购申请、审批、订单、收货、付款。它与飞书深度联动，利用飞书的审批流、消息通知和多维表格实现轻量化运营。

1.3 为什么两者联动？

FDE 的核心能力是「把 AI 嵌入业务流程」。本项目的联动设计模拟了真实 FDE 工作场景：

ERP 提供什么

  • 真实业务流程（采购审批链路）
  • 结构化业务数据（采购单、供应商、物料）
  • 遗留系统集成模式（RESTful API）

FDE 提供什么

  • AI Agent 嵌入业务流程
  • 智能风险识别与决策辅助
  • 人机协作的审批工作流
联动闭环 ERP 产生业务数据 → FDE Agent 读取并分析 → 生成风险判断和决策建议 → 路由到人工审批（高风险）或自动通过（低风险）→ 结果回写 ERP 并推送飞书通知。

4.2 LangGraph 工作流

from langgraph.graph import StateGraph, END

# 定义状态
class ProcurementState(TypedDict):
    purchase_request: dict
    risk_score: float
    risk_analysis: str
    supplier_report: dict
    approval_decision: str
    needs_human_review: bool

# 构建工作流
workflow = StateGraph(ProcurementState)

# 添加节点
workflow.add_node("analyze_risk", risk_analysis_agent)
workflow.add_node("research_supplier", supplier_research_agent)
workflow.add_node("decide_approval", approval_advisor_agent)
workflow.add_node("route_to_human", human_review_router)  # 高风险路由
workflow.add_node("auto_approve", auto_approval_action)

# 条件路由：高风险 → 人工审批；低风险 → 自动通过
workflow.add_conditional_edges(
    "decide_approval",
    route_by_risk_level,  # risk_score >= 70 → human, else → auto
    {
        "human_review": "route_to_human",
        "auto_approve": "auto_approve"
    }
)

# 定义边
workflow.set_entry_point("analyze_risk")
workflow.add_edge("analyze_risk", "research_supplier")
workflow.add_edge("research_supplier", "decide_approval")
workflow.add_edge("route_to_human", END)   # 推送飞书审批流
workflow.add_edge("auto_approve", END)
人机协作节点 route_to_human 是 LangGraph 中的人机协作节点。当 Agent 判定风险等级 ≥ 70 分时，流程暂停并推送至飞书审批流，等待人工审批。审批结果通过飞书 Webhook 回调后，流程恢复并更新状态。

五、高风险人工审批功能

5.1 触发条件

维度触发条件风险权重说明
金额单笔采购金额 ≥ 50,000 元+30大额采购需人工复核
新供应商首次合作的供应商+25无历史交易记录
品类异常采购品类与部门历史不符+20偏离正常采购模式
供应商风险尽调发现工商异常/舆情风险+25信用风险信号
频率异常同一供应商短期多次采购+15可能拆分规避审批
超预算采购金额超出部门预算+20预算控制失效
风险评分规则 综合风险评分 = 各维度权重之和（满分 100）。
≥ 70 分：强制人工审批（不可跳过）。40-69 分：建议人工审批，可由高级审批人选择跳过。< 40 分：自动通过。

5.2 审批状态流转

待提交 → Agent 分析中 → 待审批 → 审批中 → 已通过
待提交 → Agent 分析中 → 待审批 → 审批中 → 已驳回
待提交 → Agent 分析中 → 待审批 → 已撤回
待提交 → Agent 分析中 → 待审批 → 超时自动升级

状态转移规则

源状态触发动作目标状态前置条件
待提交提交审批Agent 分析中表单校验通过
Agent 分析中分析完成，风险 ≥ 70待审批Agent 输出结果
Agent 分析中分析完成，风险 < 40已通过Agent 输出结果
待审批审批人接受审批中审批人有权限
审批中审批通过已通过审批意见已填写
审批中审批驳回已驳回驳回理由已填写
待审批 / 审批中申请人撤回已撤回仅申请人可操作
待审批超过 48 小时未处理超时自动升级升级至上级审批人

5.3 角色权限

角色可执行操作数据可见范围审批额度
申请人 创建/编辑/提交/撤回采购申请 仅自己的申请 —
部门审批人 查看/审批本部门采购单 本部门采购单 ≤ 100,000 元
高级审批人 查看/审批所有采购单；可跳过 40-69 分建议审批 全部采购单 ≤ 500,000 元
系统管理员 配置风险阈值、管理审批流、查看审计日志 全部数据 无限制

5.4 异常处理

异常场景处理策略通知方式
审批超时（48 小时未处理） 自动升级至上级审批人；原审批人收到催促通知 飞书消息 + 群通知
审批人不在（请假/离职） 管理员可转移审批任务至备用审批人 飞书消息通知双方
申请人撤回 待审批状态可直接撤回；审批中需审批人确认 飞书消息通知审批人
Agent 分析失败 标记为「待人工审核」，跳过 Agent 判断直接进入人工审批 飞书消息通知管理员
飞书 Webhook 回调失败 重试 3 次（指数退避）；失败后标记为「回调异常」，管理员手动同步 飞书消息通知管理员

事件通知对象通知渠道消息内容

六、飞书集成

6.1 集成点

审批流

高风险采购单自动创建飞书审批实例，附带 Agent 风险分析报告。审批人可在飞书内直接通过/驳回，结果通过 Webhook 回调同步至 ERP。

消息通知

通过飞书机器人推送结构化消息卡片，包含采购摘要、风险等级、快捷操作按钮。支持群通知（库存预警）和私聊通知（审批提醒）。

多维表格

供应商信息、基础数据双向同步至飞书多维表格，方便业务人员在飞书内查看和编辑，数据变更自动同步回 ERP。

通讯录

同步飞书通讯录获取员工信息和组织架构，用于审批流的自动路由（按部门匹配审批人）。

6.2 Webhook 回调设计

# 飞书审批回调处理
@app.post("/api/v1/webhooks/feishu-approval")
async def feishu_approval_callback(request: Request):
    payload = await request.json()
    
    # 验证签名
    if not verify_feishu_signature(payload):
        raise HTTPException(status_code=403)
    
    event = payload.get("event")
    approval_code = event.get("code")        # 飞书审批实例 ID
    status = event.get("status")             # APPROVED / REJECTED
    
    # 查找对应采购单
    purchase_request = await db.get_purchase_request_by_feishu_code(approval_code)
    
    if status == "APPROVED":
        await purchase_request.approve(approver_comment=event.get("comment"))
    elif status == "REJECTED":
        await purchase_request.reject(reason=event.get("comment"))
    
    # 更新 LangGraph 状态
    await agent_workflow.update_state(
        request_id=purchase_request.id,
        approval_status=status
    )
    
    return {"code": 0}

10.1 体现 PDE 方法论

在文档和面试中明确展示你遵循 PDE 框架（月之暗面/Kimi 的核心方法论）：

P — Process 业务流程拆解

拆解 ERP 采购流程，定义 Agent 嵌入点。不是先做 Demo 再适配业务，而是先理解完整业务链路，厘清 AI 与人的权责边界。

D — Data 企业私有数据工程

对接 ERP 历史采购数据，构建供应商风险知识库。使用真实数据（模拟）而非筛选后的优质样本，从源头抑制模型幻觉。

E — Engine 智能 Agent 引擎编排

用 LangGraph 编排多 Agent 协作，实现提示词版本管理、工具调用、安全护栏、全链路可观测。

人机边界设计

高风险强制人工审批（Agent 辅助但不替代），低风险自动通过。体现对 AI 落地中「权责边界」的深度理解。

10.2 展示落地能力

  • 完整部署文档：docker-compose 一键部署，面试官可在 10 分钟内跑起来
  • 真实数据 Demo：提供模拟数据集，含正常采购和异常采购案例
  • 评测指标：Agent 风险识别准确率、响应时间、误报率
  • 端到端演示：从提交采购申请 → Agent 分析 → 飞书审批 → 结果回写

10.3 体现业务理解

面试时不只是讲技术，要能解释「为什么这样设计」：

  • 为什么高风险要人工审批？ — 金融/采购场景对准确度要求极高，AI 辅助但不替代人的决策权责
  • 为什么用 LangGraph 而不是 Dify？ — 需要展示复杂 Agent 编排能力（状态机、条件路由、人机协作节点），LangGraph 更适合
  • 为什么和飞书联动？ — 模拟真实 FDE 场景：对接客户现有办公系统，而非让客户切换到新平台
  • 审批超时升级逻辑？ — 来自真实企业审批场景的需求，避免审批单积压

10.4 面试讲解建议

  1. 先讲故事：「这个项目模拟了 FDE 在客户现场的真实工作——把 AI 嵌入 ERP 采购流程」
  2. 展示闭环：端到端演示完整流程（提交 → Agent 分析 → 人工审批 → 结果回写）
  3. 强调取舍：为什么选 LangGraph、为什么风险阈值是 70、为什么超时是 48 小时
  4. 展示工程能力：Docker 一键部署、CI/CD、测试覆盖
